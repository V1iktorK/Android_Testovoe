## 6. Порядок выполнения (по алгоритму)

1. **Инструменты** (день 1): `git init`, структура репо, загрузка Godot 4.x + Android export templates, Gradle 8.x + AGP (JAVA_HOME=OpenJDK17 Unity, ANDROID_HOME=SDK Unity), smoke-сборка пустых проектов во всех 4 стеках.
2. **Тестовые каркасы** (день 1–2): по одному раннеру на стек: JUnit (Java/Kotlin), headless-раннер GDScript (Godot), Unity Test Framework EditMode (Unity). Плюс `smoke-all.ps1`.
3. **Игры волнами по 4–5 штук**: для каждой игры — фиксация осей A/B/C → тесты (`tests/`) → реализация → прогон тестов (если падают — правки и повтор) → повторный прогон → обновление `REGISTRY.md` → README + screenshot.png → сборка APK → артефакты в `artifacts/` → коммит `feat: add game XX - [название]` → push.
   - Волна 1 (дни 2–5): 01–05
   - Волна 2 (дни 6–8): 06–10
   - Волна 3 (дни 9–11): 11–15
   - Волна 4 (дни 12–13): 16–20
   - День 14: финальный прогон всех тестов, сборка всех APK, инвентаризация артефактов, отчёт.
4. **Отчёт** — только в конце: папки в GitHub, ссылки на Диск, жанры/инструменты, что не получилось и почему.

## 7. Тесты (пишу до реализации, для каждой игры)

- Unit-тесты правил и генераторов: гарантия решения головоломок, проходимость уровней, баланс экономики, отсутствие тупиков, корректность save/load.
- Smoke: проект компилируется, APK собирается без ошибок, скриншот генерируется.
- Регрессия: перед каждым коммитом — повторный прогон тестов игры и общего набора.

## 8. Риски

| Риск | Митигация |
|---|---|
| Мало места на диске (36 ГБ) | Чистка Gradle/временных каталогов после каждой волны; APK не коммитить в git |
| Godot-экспорт требует ~1 ГБ шаблонов | Ставлю один раз, переиспользую для 5 игр |
| Нет эмулятора | Smoke через headless + успешный build APK; при подключении устройства — `adb install` |
| Объём «полноценных игр» при 20 проектах | Типовой контент-набор на игру: меню + 20 уровней/волн + апгрейды + рекорды + звук (процедурный) |
| Сбои сети при загрузке зависимостей | Повторы, кеширование, поэтапная загрузка |
